# be-DailyJob 

> 이 회고는 작업량을 보고하기 위한 문서가 아니라, 
> 오늘 내가 어떤 판단을 했고 어떤 개발 행동을 반복하거나 바꿔야 하는지 확인하기 위한 기록입니다. 
> 각 항목은 길게 쓰기보다, 사실/판단/근거/다음 행동이 드러나게 구체적으로 작성하세요.

### 1. 오늘 완료한 것
- 오늘 실제로 끝낸 기능/수정/학습:
  - Order 도메인 구현 (정산, 취소 관련은 wallet 도메인이라 추후에 담당 정하기)
  - 같이 테스트 돌리면서 원인 찾기
    - 동접500, RPS 50 입찰 요청에 대해 응답시간 p95, p99이 원래 8s, 9s 였다.
    - 입찰이벤트를 수신해 sse broadcast하는 코드가 Executor 없이 동기로 처리되고 있는 걸 발견했다.
    - 접속한 유저가 많으면 그 유저들한테 sse 전송 다 될때까지 기다려야했고, 그 중 일부가 전송이 지연되면 그만큼 입찰 요청 유저가 응답받는 시간이 지연되었다.
    - 이걸 ThreadPoolTaskExecutor에게 execute로 넘겨서 병렬처리하도록 바꿨고, sse 전송이 다 되길 기다릴 필요없이 (거의) 즉시 응답을 요청자에게 반환하게 되었다.
    - 그래서 응답시간이 789ms, 2s로 바뀌었다.
    - 레디스로 아예 입찰 판정을 옮기면 더 빠르게 처리가 가능할 것 같다.
- (오늘의 목표 중에서) 아직 끝내지 못한 부분:
  - 다중 인스턴스 대비 알림 저장, SSE 발송, 복구 로직 수정

### 3. 오늘 못한 것
- 하다보니까 Port-Adapter 구조를 전혀 지키지 않았다는 것을 은기님을 통해 알게 되었다. 사실은 알고 있었다.
  - 내 생각에는 짧은 프로젝트 기간동안에 port만들어 놓고 adapter 구현해주기를 기다리는 것이 개발에 딜레이가 되는 것이라고 처음에 생각했다.
  - 그래서 그냥 도메인 담당하시는 분한테 여기 코드 좀 추가하겠다 말씀 드리고 직접 추가했는데 이게 서로의 영역을 침범하는 게 되었다.
  - 사실 포트-어댑터 구조를 잘 지키고 Mock data와 Mock adapter을 사용해서 내가 짜는 로직이 잘되는 걸 확인하는 구조로 가면 오히려 딜레이가 사라지는 구조인데 내가 그걸 잘 이해 못하고 그냥 개발 혼자할 때 처럼 이게 빠르지 않나? 혼자 판단했던 것 같다.
  - 이 사실을 이해하고 나서는 굉장히 좋은 구조라고 생각했는데, 오히려 은기님이나 다른 분들이 오버엔지니어링이라 여기시고 걷어내는 게 좋다고 말씀하셔서 아쉬웠다.
  - 이제 그냥 도메인 경계 딱히 없이 그냥 자기 필요한 거 넘어가서 구현하면 되지 않냐고 말씀하셨다.
  - 그렇게 규칙이 사라지니까 오히려 이게 어디까지 되는 거고 어디는 넘으면 안되는 건지 애매해져서 조금 해메게 되었다.
  - 그래서 그냥 내 도메인이 아닌 부분을 일단 이슈로 빼놓고, 누가 구현할 지 나중에 결정하는 식으로 빼놓았다.
